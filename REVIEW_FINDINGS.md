# Review Findings

| Severity | Datei:Zeile | Code-Zitat | Problem | Fix-Vorschlag |
|----------|-------------|------------|---------|----------------|
| MEDIUM | server/currency.js:99-104 | `const current = await getBalanceMemory(playerName); const newBalance = normalizeMoney(current + amount); balances.set(playerName, newBalance);` | `addBalance()` im In-Memory-Fallback (kein `DATABASE_URL`) liest `current` und schreibt `newBalance` OHNE `withBalanceLock`, während `deductBalance()` (Z.172-179) und `addDiamonds()` (Z.283-288) im selben Modul denselben Lock-Mechanismus konsequent nutzen. Zwei gleichzeitige `addBalance`-Aufrufe für denselben Spieler (z.B. zwei parallele Gewinnauszahlungen) können beide denselben `current`-Wert lesen und sich gegenseitig überschreiben ("lost update") — eine Auszahlung geht silently verloren. Da `await getBalanceMemory()` einen Event-Loop-Tick durchläuft, ist die Race real erreichbar, sobald zwei Socket-Events für denselben Spieler quasi gleichzeitig eintreffen. | `addBalance` im Memory-Zweig ebenfalls mit `withBalanceLock(playerName, async () => {...})` umschließen, analog zu `deductBalance`. |
| HIGH | server/currency.js:243-257 | `const currentBalance = await getBalanceMemory(playerName); if (cost > currentBalance) return null; ... balances.set(playerName, newBalance); ... diamonds.set(playerName, newDiamonds);` | `buyDiamonds()` im In-Memory-Fallback macht einen kompletten Read-Check-Write über zwei Maps (`balances`, `diamonds`) OHNE jeglichen Lock. Zwei parallele `buyDiamonds`-Aufrufe für denselben Spieler können beide denselben `currentBalance` lesen, beide die `cost > currentBalance`-Prüfung bestehen und beide abziehen — das Ergebnis ist eine negative Balance (Double-Spend) und doppelte Diamant-Gutschrift, obwohl der Spieler nur einmal genug Guthaben hatte. Genau das Muster, vor dem `withBalanceLock` in `deductBalance` schützt, fehlt hier. | Den gesamten Memory-Zweig von `buyDiamonds` in `withBalanceLock(playerName, async () => {...})` einwickeln, wie es `deductBalance`/`addDiamonds` bereits tun. |
| MEDIUM | server/identity.js:40-44 | `async function setOwnerInDb(playerName, ownerToken) { if (!isDatabaseEnabled()) { memoryOwners.set(playerName, ownerToken); return true; } }` | Im In-Memory-Fallback ist `setOwnerInDb` ein bedingungsloses `Map.set` — anders als der DB-Zweig darunter, der per `where owner_token is null` ein TOCTOU-sicheres conditional update macht. Zwei parallele `claimName`-Aufrufe für denselben, bisher unclaimten Namen mit unterschiedlichen Owner-Tokens lesen in `getOwnerFromDb` beide `null`, und `setOwnerInDb` überschreibt dann einfach den zuvor gesetzten Token des jeweils anderen Callers ("last write wins" statt "first claim wins"). Der zweite Aufruf gibt fälschlich `{ ok: true, firstClaim: true }` zurück, obwohl der Name inzwischen schon vom ersten Token geclaimt wurde — ein Name kann im Memory-Modus von zwei Browsern gleichzeitig "erfolgreich" geclaimt werden, was dem TOFU-Sicherheitsziel widerspricht. | `setOwnerInDb` im Memory-Zweig analog zum DB-Zweig bedingt machen, z.B. `if (memoryOwners.has(playerName)) return false; memoryOwners.set(playerName, ownerToken); return true;` |
| MEDIUM | server/achievements.js:326-330 | `if (await isAlreadyUnlocked(...)) continue; const inserted = await recordUnlock(...); if (inserted) { const rewards = await grantReward(playerName, a); ... }` | `recordUnlock` (eigene DB-Query, sofort committed) und `grantReward` → `addBalance`/`addDiamonds` (jeweils eigene, separate `withTransaction`) laufen NICHT in derselben Transaktion. Schlägt die Reward-Vergabe nach erfolgreichem `recordUnlock` fehl, bleibt der Achievement-Unlock dauerhaft in der DB stehen, aber die Belohnung wurde nie gutgeschrieben. Da `isAlreadyUnlocked` danach `true` liefert, kann die Belohnung auch nie nachträglich nachgeholt werden — der Spieler verliert sie endgültig. | `recordUnlock` und `grantReward` in eine gemeinsame Transaktion einbetten (`client` durchreichen), damit ein Fehler in der Belohnungsvergabe auch den Unlock zurückrollt. |
| LOW | server/daily-streak.js:188-213 | `// Reward credit happens outside this UPDATE so the streak row is committed even if the wallet write fails. return { ok: true, ..., _pending: true }; }).then(async (res) => { ... newBalance = await addBalance(...); }` | Bewusst dokumentierter Trade-off: der Streak-Zähler wird in einer eigenen Transaktion committed, die Coin-/Diamond-Gutschrift läuft danach separat. Schlägt die Gutschrift fehl, bleibt `last_claimed_day` auf "heute geclaimt" stehen und der Spieler kann den Claim für diesen Tag nicht wiederholen — die Belohnung ist unwiderruflich verloren, obwohl `ok: true` zurückgegeben wird. Kein Double-Spend/negative Balance, aber ein stiller Reward-Verlust im Fehlerfall. | Fehlerfall im `.then()`-Handler abfangen und bei Fehlschlag loggen + Warnung statt stillem `newBalance: null` zurückgeben, oder Reward-Gutschrift in einen Retry-/Ledger-Mechanismus überführen. |
| LOW | server/index.js:210-218 | `if (GAME_ENABLED && stocksRouter.fetchTickerQuotes) { setInterval(() => { stocksRouter.fetchTickerQuotes()...  }, 5 * 60 * 1000); }` | Der Ticker-Background-Refresh-`setInterval` wird nirgends referenziert/gecleart. `gracefulShutdown()` ruft weder `clearInterval` dafür auf, noch existiert ein Handle dafür. Aktuell unschädlich (hartes `process.exit(0)`), aber bei erneutem Modul-Load (Tests, Multi-Instanz) akkumulieren sich nicht bereinigte Intervalle. | Interval-Handle in einer Modulvariable speichern und in `gracefulShutdown` per `clearInterval` stoppen, konsistent mit `stopMatchChecker()`/`stopKeepAlive()`. |
| LOW | server/portfolio-history.js:8,18-20 | `const history = new Map(); ... if (!history.has(playerName)) { history.set(playerName, []); }` | Der äußere `history`-Map (playerName → Snapshot-Array) hat KEINE Eviction — jeder Eintrag bleibt für die gesamte Prozesslaufzeit bestehen, auch wenn der Spieler nie wieder aktiv ist. Nur das innere Array pro Spieler ist auf `MAX_SNAPSHOTS = 100` begrenzt. Bei vielen unterschiedlichen (auch kurzlebigen/Test-)Spielernamen wächst der Map unbegrenzt — ein klassischer langsamer Memory Leak, den der periodische Cleanup in `server/cleanup.js` nicht erfasst. | TTL/LRU ergänzen (z.B. `lastAccess`-Zeitstempel pro Spieler und periodische Bereinigung alter Einträge), oder History in die DB auslagern. |
| HIGH | server/turkish-streaks.js:77-119 | `const current = await client.query('select ... from turkish_streaks where player_id = $1', ...); ... const { currentStreak, alreadyCompleted } = computeNextStreak(...); ... await client.query('update turkish_streaks set ... where player_id = $4', ...); ... if (rewardCoins > 0) { await addBalance(...); }` | Klassisches TOCTOU-Muster im DB-Modus: `SELECT` liest `last_completed_day`, die Anwendung entscheidet in JS ob `alreadyCompleted`, danach folgt ein einfaches `UPDATE ... where player_id = $4` OHNE Bedingung auf den zuvor gelesenen Zustand (kein `WHERE last_completed_day IS DISTINCT FROM $3`, kein `SELECT ... FOR UPDATE`). Zwei parallele `POST /api/turkish/complete`-Requests für denselben Spieler (Doppelklick, Retry, zwei Tabs) lesen unter READ COMMITTED denselben `last_completed_day`, berechnen beide `alreadyCompleted: false` und zahlen beide die Streak-Belohnung aus — der Spieler kassiert den Tages-Reward doppelt. Anders als das strukturell identische `server/daily-streak.js` (atomares `UPDATE ... where ds.last_claimed_day is null or ds.last_claimed_day < $2 returning ...`) fehlt hier der bedingte Atomic-Update-Guard komplett. | Das `UPDATE` bedingt machen und über `returning` prüfen, ob es gegriffen hat, analog zu `server/daily-streak.js`; bei leerem Ergebnis `{ ok: true, alreadyCompleted: true, rewardCoins: 0 }` zurückgeben statt der optimistischen Read-Then-Write-Logik. |
| LOW | server/lol-betting.js:6-39 | `const betsMemory = []; let nextBetId = 1; ... betsMemory.push(bet);` | Im In-Memory-Fallback wächst `betsMemory` unbegrenzt — abgelaufene/resolved/refunded Bets werden nie aus dem Array entfernt, nur ihr `status`-Feld ändert sich. Alle Lookup-Funktionen iterieren linear über das gesamte Array, was zusätzlich zur Speicher- auch zur CPU-Last mit der Zeit wird. | Resolved/refunded Bets nach einer Aufbewahrungsfrist aus `betsMemory` entfernen (z.B. aus dem periodischen Cleanup in `server/cleanup.js` heraus), oder auf eine Map mit expliziter Eviction umstellen. |
